# Testing

The repo uses layered validation so CLI behavior, service contracts, and live compatibility are exercised separately.

## Local checks

```bash
uv run ruff check .
uv run mypy src
uv run pytest
uv run python tools/check_catalog_schema.py
uv run python tools/check_command_coverage.py
uv run python tools/check_release_version.py --tag v7.4.0
uv build
```

Optional `just` aliases:

```bash
just check
just test
just snapshot
```

## Test layers

- unit tests for models, service contracts, config/auth resolution, and helpers
- snapshot tests for CLI help behavior
- integration tests for compatibility entrypoints and wiring
- integration and unit coverage for workflow template rendering and workflow VM initialization paths
- contract and golden tests for imported private live observations
- E2E tests for live OpenNebula validation when environment variables are present

## Read-only live capture

Capture sanitized live observations without sharing credentials:

```bash
tools/capture_live_readonly.sh --write-artifact > /tmp/opennebula-capture.jsonl
uv run python tools/import_live_capture.py import --input /tmp/opennebula-capture.jsonl
```

That workflow:

- executes only allowlisted `--help`, `list`, and `show` commands
- redacts endpoints, hostnames, IPs, MACs, and secret-like fields
- stores private artifacts under `refs/tasks/live-capture/`
- updates the private context store and KB export locally

## Remote OpenNebula E2E workflow

For disposable validation VMs, use the `assh`-backed harness:

```bash
ONE_E2E_TARGET_ALIAS=opennebula-e2e \
ONE_E2E_TARGET_ENDPOINT=root@vm.example.com \
ONE_E2E_REMOTE_ROOT=/mnt/opennebula-cli-e2e \
ONE_E2E_MODE=manual-frontend \
ONE_E2E_VALIDATE_LOCAL=1 \
bash tools/e2e_run_live.sh
```

The harness:

1. bootstraps the selected OpenNebula compatibility line on the remote Ubuntu `24.04` host
2. seeds disposable `e2e-*` fixtures through official OpenNebula CLI tools
3. tunnels the XML-RPC endpoint back to the local checkout
4. runs live read-only and mutation E2E from the current repo state
5. imports sanitized read-only capture data
6. cleans up disposable `e2e-vm-*` resources

## Remote fixture scripts

The harness uses:

- `tools/e2e_bootstrap_opennebula.sh`
- `tools/e2e_seed_fixtures.sh`
- `tools/e2e_cleanup_fixtures.sh`
- `tools/e2e_run_live.sh`

Fixture rules:

- disposable resources use the `e2e-*` namespace
- cleanup only removes `e2e-vm-*` VMs unless explicitly told to reset base fixtures
- base fixtures are designed to be idempotent across repeated runs

## Release validation for `7.4.0`

The 7.4 candidate was validated in separate evidence layers:

- DR OpenNebula `7.4.0`, read-only only: authenticated version negotiation; list/show/full on VM, host, image, template, vnet, datastore, and cluster through PyONE and raw XML-RPC; ACL list; and OneFlow service/role state pairs
- local OpenNebula `7.0.2` protocol fixture: PyONE and raw list/show plus clean rejection of 7.4-only capabilities
- OpenNebula 7.4 source binding: generated from the tagged schema, imported successfully, and passed focused transport/service tests
- local OneForm REST fixture: versioned routes, path encoding, redirect rejection, response limits, credential scoping, and preview isolation
- mutation contracts: exact upstream signatures, context denial before contact, non-idempotent no-replay, and aggregate partial failures

The historical disposable 7.0 environment evidence remains the real-server mutation baseline for:

- `template instantiate`
- `vm poweroff --wait`

No production mutation was performed for 7.4. OneForm was not configured in DR. New 7.4 mutations require disposable `e2e-*` validation before environment enablement.
