# Architecture

The implementation is organized as a layered CLI and SDK so operator workflows, automation flows, and Python integrations all pass through the same typed core.

## Layers

1. `cli/`
   Typer command tree, root option handling, help examples, and user-facing error mapping.
2. `compat/`
   Official-style wrappers such as `onevm`, `oneimage`, and `onevnet`.
3. `auth/` and `config/`
   Profile loading, auth resolution, env precedence, and runtime configuration.
4. `transports/`
   PyONE and raw XML-RPC routing, pre-I/O policy enforcement, plus explicit plugin REST transport.
5. `services/`
   Reusable typed operations consumed by both the CLI and the SDK, including workflow rendering and VM initialization helpers.
6. `sdk/`
   Public `OneClient`, exceptions, and normalized models.
7. `renderers/`
   Human-readable and machine-readable output handling.
8. `waiters/`
   Polling-based lifecycle waiting for long-running operations.
9. `registry/` and `catalogs/`
   Independently materialized 7.0 and 7.4 command profiles, authenticated negotiation, and parity tracking.
10. `plugins/`
    OneFlow, OneGate, and OneForm extension boundaries.
11. `dev/`
    Local maintainer tooling such as the private context store and live capture support.

## Design rules

- keep CLI handlers thin
- normalize backend payloads before they reach users
- keep machine output deterministic
- implement reusable logic in services first
- track parity explicitly in catalogs
- keep read-only live observation tooling aggressively redacted
- choose a backend before I/O and never replay a failed non-idempotent request
- derive OneFlow-compatible endpoints only where defined; require an explicit OneForm endpoint
- enforce read-only context policy at the service and transport boundaries

## Current coverage

- `vm`
- `host`
- `image`
- `template`
- `vnet` (read-only)
- `datastore` (read-only)
- `cluster` (read-only)
- `workflow template` (`init`, `render`, `import`, `apply`)
- `workflow vm` (`init`, `apply`)
- 7.4 VM exec/VM-group, cluster-plan, group-VLAN, and OneFlow schedule operations
- OneForm driver, provider, and provision services with guarded template previews

## Why this matters for DevOps users

This structure is intentional:

- shell users get a stable CLI contract
- pipeline users get deterministic structured output
- Python users get typed access to the same operations
- maintainers only have one behavior path to validate live
