# SDK

The public SDK entrypoint is:

```python
from opennebula_cli.sdk import OneClient
```

## Constructors

```python
OneClient.from_env()
OneClient.from_profile("prod")
OneClient.from_config(config)
```

## Current services

- `client.vm`
- `client.host`
- `client.image`
- `client.template`
- `client.vnet`
- `client.datastore`
- `client.cluster`

## CLI and SDK relationship

The CLI is a thin layer over the same service objects exposed by the SDK.

That means:

- CLI behavior should be implemented in services first
- SDK and CLI share normalized models
- transport details stay below the public service boundary

Workflow note:

- `one workflow template` and `one workflow vm` currently ship as CLI automation surfaces.
- their reusable logic lives in service-layer internals, but there is no stable public SDK facade for workflow orchestration yet.
- see `docs/workflows-vm-templates.mdx` for current workflow usage.

## Operator automation example

```python
from opennebula_cli.sdk import OneClient

client = OneClient.from_env()

running = [
    vm
    for vm in client.vm.list()
    if vm.state.upper() == "ACTIVE"
]

for vm in running:
    print(vm.id, vm.name, vm.host)
```

## Profile-based example

```python
from opennebula_cli.sdk import OneClient

client = OneClient.from_profile("prod")
template = client.template.show(24)
print(template.id, template.name)
```
